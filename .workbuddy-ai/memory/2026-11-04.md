- **本任务最关键的事实**：**`rules/loader.rs` 在扫描链路上没有任何消费者**。它只服务 `external_deny_list`（L3 外部红线）与规则库更新/回滚比对，5 个内置模块各自硬编码路径。所以「改 loader 就能让用户规则生效」是错的——必须新增 `scan/modules/user_rules.rs` 才让「加规则→扫描→有条目」成立。
- **三道过滤缺一不可**：glob 匹配 → **逐条真实路径过 `whitelist::classify`**（创建时校验的是「模式的静态根」，通配符可能展开到子目录里的敏感文件，两者不能互相替代）→ `covered_by_builtin` 内置优先（否则 `%TEMP%\*` 会让同一批文件出现两遍）。
- **两处安全决策**：① `risk_level` 只允许 L1/L2，DB 层 `CHECK` 挡死 L3——L3 语义是「红线永不删除」，一条 L3 的清理规则会扫出永远删不掉的条目，自相矛盾；② 每条规则 20,000 条上限 + 回调式遍历，否则指向几十万文件的目录会跑几十分钟并写爆 `cleanup_item`。
- **真实升级验证**：仓库 `data/cdiskcleaner.db` 恰好是 **v1 时代**的库（9 张表），复制副本按 MIGRATIONS 顺序实测 **v1→v4 全通**（drive_letter 生成列 + user_rules + 两个索引都在），既有数据无损。
- **端到端证据**：`end_to_end_rule_produces_items_then_disabled_removes_them` —— 真 DB + 真临时目录 + 真 `run_all`：加规则 → 出现 `module_code='user_rules'` 条目 → 停用 → 新 session 0 条。
