### 版本号升级的完整清单（现在有两次经验了）

**必改 4 处 + lock**：`app/package.json`、**根 `package.json`**、`app/src-tauri/tauri.conf.json`、`app/src-tauri/Cargo.toml`、`Cargo.lock`（cargo check 自动）。

**容易被任务书漏掉、但必须同步的 2 处「版本展示行」**：
- `README.md` 的「当前版本：**vX.Y.Z**」
- `docs/USER_GUIDE.md` 的「适用版本：**vX.Y.Z**」

这两处不是功能描述，是版本号展示。不改的后果是**仓库自相矛盾**（CHANGELOG 说 0.2.1、README 说 0.2.0，用户看首页会以为最新还是 0.2.0）。任务书写「不修改 README/手册」时，那句的意图是「不重写功能列表」，别当成「连版本行都不许动」。

**不该改的 2 处**：`engine`/`elevation` 的 `0.1.0`（内部构件不单独发版）；`latest.json` 的 `0.1.0`（CI 的 `generate-latest` 用真实签名整份覆盖，手改会造出签名对不上的假清单）。

### CHANGELOG 写 patch 段的经验

- **patch 语义不设「新增 / 变更」**，只写「修复」。设了空段反而是噪音。
- **根因要翻译成用户能懂的话**。任务书给的「提权命令名从未进入 argv 数组」是给开发看的；用户版应写成「拉起提权程序的命令行里漏了命令名，提权程序收到的第一个参数是 --result，白名单不认，直接以未知命令退出（退出码 3）且不写结果文件」。

### 核心设计：方案存「路径三元组」而不是 item id

`cleanup_plan.item_refs` 存 `{module_code, category, path}`。原因写在表注释里：
**`cleanup_item.id` 每次扫描都是新的一批**，用 id 存方案，下次扫描整份失效。

由这个约束推出三个必须做的决定（都容易漏）：
1. **回查取 `id` 最大那行**。`cleanup_item` 跨扫描累积，同路径可能有多行；全取会让
   「12 条方案」在界面上勾出 30 个框，用户以为方案坏了。
2. **匹配不到的进 `unmatched`，不静默丢弃**。悄悄少勾几条比报错更糟。
3. **`matchedCount` 与 `itemCount` 分开返回**。12 条只匹配 3 条时必须能说清
   「12 条（本次匹配 3 条）」；只显示 3 会让人以为数据丢了。

`save_plan` 收 `item_ids` 而不是三元组——**前端 `PendingItem` 里没有 `category`**，
拼不出完整三元组，让后端反查更可靠。

### 跨页通信（没有状态管理库时的做法）

App 持一份 state 当中间人，prop 下发——`Dashboard` 的 `scanSignal` 就是这个先例。
两个要点：
- **回调必须 `useCallback` 固定引用**。Items 的「上报勾选」effect 依赖 `onSelectionChange`，
  每次渲染新建函数会让 effect 反复执行 → 无限 `setState`。
- **载荷一次性消费**：套完立刻 `onPlanConsumed()` 清空，否则翻页回来会把同一份方案
  再套一遍，覆盖用户后来的手动勾选。

### 能力边界：没有文件选择框

本项目**没引 `tauri-plugin-dialog`**。所以导出只能「写固定目录 + 返回绝对路径」，
导入只能「粘贴路径」。任务书写「下载 JSON / 选择导入」——在无对话框插件时做不到。
**别为了对上一句话去引一个新插件**（涨体积、多一份 capability），把边界写清楚、界面
上显示完整路径让人复制，是更诚实的做法。

### 最有价值的一条：**「折线误导」的成因不是折线**

task-061 的代码注释明确写着「为什么用柱状而不是折线：折线会把没数据的那天画成斜线，误导」。
任务书这次要求改折线。**如果只是换个形状，那个问题会原样回来。**

真正的成因是：`cleanup_stats_trend` 的 SQL 是 `GROUP BY day`，**没记录的日期根本不返回**。
所以 10-01 和 10-20 会被画成相邻两点，中间 19 天凭空消失。

修法：`fillDays()` 按真实日历铺满整个范围、缺失补 0。再配合「>0 画实心圆点、=0 不画」，
比柱状图信息量更高且不误导。

> 规律：**遇到「前任注释说这么做有问题」，先分清是「这个方案有问题」还是「当时的实现有问题」。**
> 很多时候是后者，照抄结论会白白放弃一个更好的方案。

### 第二个：**任务书的功能设计有实质缺陷时必须停下来改**

任务书写「`schtasks /create /tr "<exe>"` 注册每日任务」。照字面做 → **每天早上 9 点弹一个完整 GUI 窗口**。
那不叫后台扫描。

必须补 `--auto-scan` 静默模式。选了「复用 Tauri 运行时 + `visible: false` + setup 显式 `show()`」，
而不是「独立 CLI 不碰 Tauri」——后者要重新实现一遍 `%APPDATA%` / `resource_dir()` 解析，
算错就静默读不到 DB 和脚本，**而且没有任何报错**，这类 bug 极难发现。

### 技术要点

- **平滑曲线用「二次贝塞尔穿中点法」**，不用 Catmull-Rom：后者在数据突变时会**过冲**，
  画出比峰值还高的点。穿中点法只用相邻两点的中点做控制点，曲线始终被数据点包住。
- **`localDayKey` 必须手写**，不能用 `toISOString().slice(0,10)`（UTC）：SQLite 侧是 `localtime`，
  东八区凌晨 0-8 点会差一天，表现为「昨天的数据跑到今天」。
- **切范围要丢弃过期响应**（`alive` 标志）：快速点 7→30→90 时慢的那个回来会覆盖成错误范围。
- **`schtasks` 全靠退出码判断，不解析输出**：输出是本地化文本（中文「成功: 成功创建计划任务」）。
  task-065 的 DISM、task-068 的 schtasks /query 都踩过同一个坑——**第三次了，以后凡是系统工具一律只看退出码**。
- **`schtasks /tr` 的路径必须加引号**：安装态在 `C:\Program Files\...`，不加引号会在空格处截断，
  任务指向 `C:\Program.exe`。
- **不要 `/ru SYSTEM`**：会要求提权，还把任务丢进 Session 0 拿不到用户通知权限——纯负收益。
  有单测断言参数表不含 `/ru` `/rp` `/rl` `/it`。
- **静默模式退出前 sleep 2s**：通知是异步投递的，进程立刻死掉 Windows 可能收不到。

### 环境坑（新）

**`schtasks.exe` 被开发沙箱的 Program Blacklist 拦截**（和 `reg.exe` 一样）：
```
PROGRAM BLOCKED BY SECURITY POLICY - schtasks.exe (C:\WINDOWS\System32\schtasks.exe)
```
所以真实往返用例走了「跳过」分支，12 条测试全绿但**没验证到 schtasks 执行**。
测试设计成「本机已注册则跳过（不动用户配置）、跑完必删、**先 disable 再断言**（断言失败也不留残渣）」，
这个模式以后测「会改系统状态」的东西都可以照抄。

### 测试教训

**改动会让既有用例失效时，要连根一起改。** task-061 的 `App.test.tsx` 用例断言了
「峰值 2.0 MB」和写死日期 `2026-10-27/29`。折线改造后：
- 峰值 → 合计（我改了文案）
- 写死日期 → **必须改成相对今天的偏移**，否则 30 天后数据落到窗口外、合计变 0，用例自动失效

第二点是最容易漏的：**写死日期的用例是定时炸弹，不是「稳定的用例」**。
