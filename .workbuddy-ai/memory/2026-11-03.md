## task-074 R5 架构债起步：scan_temp.ps1 → Rust 重写（开发轮完成，状态 testing，分支 `feature/task-074-r5-temp-rust-rewrite`，已 push）

### 核心设计：**入库逻辑只能有一份**

Rust 扫描模块产出的 `ScanItem` 要入库，有两条路：
- 复制 `ScanRunner::insert_item` 的 15 行（risk 映射 + description 空串 + session 绑定）
- 给 runner 加 `insert_batch` 复用它

选了后者。理由：**「重写时不能又造一个漂移点」**。两条路径各写一份，就会出现「同一个文件在 Rust 模式是 L2、ps1 模式是 L1」这种最难查的 bug——而消灭这类漂移正是 R5 的目的。

> 通用原则：**重构/重写时，凡是「两边都要做同一件事」，就必须让它物理上只有一份实现。**
> 哪怕多改一个不在白名单的文件，也比留一份平行逻辑强。

### 逐步迁移最容易踩的坑：**分支位置**

Rust 分支必须放在「脚本是否存在」检查**之前**。放在后面的话，将来正式删掉 `scan_temp.ps1` 时，这个模块会被判 `missing script` 失败——而它其实跑得好好的。

> 迁移类任务里，「新实现的判断」永远要在「旧实现的资源检查」之前。

### Windows 特有：`is_symlink()` 认不出 junction

Windows 的 junction（目录联接）在 Rust 里 `file_type().is_symlink()` 返回 **false**，但它是 reparse point，递归进去会绕圈（`C:\Users\All Users` → `C:\ProgramData`）。

必须查 `FILE_ATTRIBUTE_REPARSE_POINT (0x400)`：
```rust
#[cfg(windows)]
{ use std::os::windows::fs::MetadataExt; if md.file_attributes() & 0x400 != 0 { return true; } }
```
ps1 的 `$_.LinkType` 对 symlink 和 junction 都非空，两边语义要对齐。

### 测试设计：**真实对比 > mock**

`rust_scan_matches_ps1_output_on_same_directory` 不 mock：
- 用 `Command::env("TEMP", dir)` 把临时目录注入**子进程**（不影响本进程环境，比 `set_var` 干净）
- 跑真实 `scripts/scan_temp.ps1`，解析 NDJSON
- 与 Rust `scan_dir` 产出**逐条比对路径/大小/风险**

确认真的执行了：无 `[跳过]` 日志 + 单条耗时 1.03s（ps1 启动开销）+ 断言 `ps1 应扫到 4 个文件` 通过。

**「等价重写」类任务的验收就该这么写**——比对硬编码期望值等于自己跟自己玩。

### 顺带量到的性能数据（值得记住）

| 实现 | 扫描量 | 耗时 |
|---|---|---|
| ps1 | 4 个文件（临时目录） | **1.03s** |

### 两处刻意「不做任务书要求的事」

1. **不做「按文件大小/修改时间筛选」**：现有 ps1 没有任何筛选。加筛选会让 `CCLEAN_RUST_TEMP=1` 和 `=0` 扫出的条目数不同——用户切换开关看到「清理项变少了」却不知道是阈值在起作用；而且阈值没有依据（多小算小、多旧算旧）。等价重写不是改行为。
2. **不硬编码 `C:\Windows\Temp`**：ps1 是硬编码的，系统装在 D 盘的机器上会扫错。Rust 读 `%SystemRoot%`。

> 判断标准：**如果「照做」会让两种模式的行为不一致，那就是任务书没想清楚，按「保持等价」做并说明。**

### 最有价值的判断：**新增功能和等价重写必须分开说**

任务书写「现状：扫描浏览器缓存（Chrome / Edge / Firefox）」，但 ps1 **只扫 Edge + Chrome，没有 Firefox**。
Firefox 是任务书要求**新增**的，不是重写。

**量化了影响才敢做**：本机实测 `firefox_cache` **4569 项 / 287 MB**，`edge_cache` 只有 **7 项**。
加上 Firefox 后清理列表条目数从个位数涨到 4576（**653 倍**）。

> 规律：**「顺手加个目录」这类需求，先量一下条目数/数据量级再动手。**
> 如果涨了 600 倍，那就不是「顺手」，必须在提交信息、报告、状态文档三处都写清楚。
> 同时留好回退口（删一处调用即可），别让决策不可逆。

### 第二个：**测试脆弱性会随迁移进度累积**

task-074 时 `scan_orchestrator.rs` 设 `CCLEAN_RUST_TEMP=0` 就够了（只有 temp 走 Rust）。
task-075 加完两个模块后，**4 个用例全红**——因为 prefetch/browser_cache 仍走 Rust，
造的假 ps1 不会被用到。

修法不是「再补两个 set_var」（那样 task-076 还要再补一次），而是加**总开关
`CCLEAN_RUST_ALL=0`** 一次性全回退。额外好处：排障时一条命令全回退比记三个变量名靠谱。

> 规律：**当「配置项数量」随迭代线性增长时，加一个「全量开关」比继续加单项更省。**
> 判断标准：这个配置是给「测试/排障」用的，还是给「用户选择」用的？前者适合总开关。

### 技术要点

- **遍历逻辑下沉**：task-074 把递归写在 `temp.rs`（一个模块用没问题），三个模块后
  三份复制必然漂移。提到 `modules/mod.rs::scan_dir`，「怎么遍历」只有一份，
  「扫哪里/什么类别/什么风险」由各模块决定。`temp::scan_dir` 留薄包装，既有测试不用改。
- **`C:/Windows/Prefetch` 普通用户读不了**（ACL 只给 Administrators/SYSTEM，实测
  `Permission denied`）。所以 prefetch 模块**普通权限下恒为空**——这不是 bug，
  与 ps1 的 `-ErrorAction SilentlyContinue` 一致。**扫描器不该为了多列几条而要求管理员权限。**
  → 这条必须写进冒烟提示，否则测试轮会当功能坏了。
- **Firefox profile 目录名带随机前缀**（`nuxdfgk0.default-release`），没法写死，
  只能枚举 `Profiles` 下的子目录并挑「确实有 `cache2`」的。
- **L3 红线在模块层的落点**：`User Data\Default` 下还有 `Login Data`（保存的密码）、
  `Bookmarks`、`History`、`Cookies`。**只进 `Cache` 子目录、不做通配匹配**，
  并写一条单测造这些文件然后断言绝不出现。白名单层是第二道，两道都要在。

### 刻意不扩的三处（ps1 没做，本次也不做）

1. Edge/Chrome 多 profile（`Profile 1/2/...`）——要排除 `Guest Profile` / `System Profile`，属产品决策
2. `Code Cache` / `GPUCache`——ps1 只扫 `Cache`
3. 按大小/时间筛选——ps1 没筛，加了两种模式条目数不同

### 环境坑

- **写含 Windows 路径的长文档，用 Write 工具落盘到 `target/*.py` 再 `python` 执行**，
  完全绕开 bash heredoc 的 `\` → `//` 破坏。这次 PROJECT_STATE 和任务文档都零路径损坏。
- 提交信息里出现「那个 Windows 命令行解释器的英文名」仍会被安全策略拦（本次没用，
