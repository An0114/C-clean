**最重要的一条：任务书把 updater 的 JS API 写错了，必须看 `.d.ts` 而不是照抄任务书。**

`@tauri-apps/plugin-updater@2.13.3` 真实签名：

```ts
downloadAndInstall(onEvent?: (progress: DownloadEvent) => void, options?: DownloadOptions & InstallOptions): Promise<void>
```

- **第一个参数就是回调**，不是任务书说的 `{ onEvent }` 对象（写成对象 TS 直接编译失败）。
- 事件字段是 `data.contentLength` / `data.chunkLength`，**不是** `totalSize` / `chunkSize`。
- **`contentLength` 是 optional** —— 服务器不给 Content-Length 时拿不到总量，`total=0` 的兜底是必需项，不是可选优化。
- `Finished` 事件没有 `data`。

以后凡是「给现有库加回调/事件」的任务，先去 `node_modules/.../dist-js/index.d.ts` 看真实签名，再动手。

**两个设计决策（以后会再遇到）**：
- **跨事件累计的值放 `useRef`，不要靠 `setState` 的函数式 updater**。速度估算需要「窗口起点的字节数」，若在 `setDownload(prev => ...)` 的 updater 内部再调 `setSpeed`，属于「updater 里产生副作用」，React 严格模式会重复执行 updater → 速度算两遍。ref 做真值、setState 只驱动渲染。
- **共享纯函数必须独立文件**，不能塞进组件。两条硬约束：① 组件文件多导出非组件会触发 `react-refresh/only-export-components`；② `Settings` 要复用函数，而 `App` import `Settings`，函数放 `App` 里会造成 **App ↔ Settings 循环依赖**。所以新建了 `app/src/utils/update.ts`（白名单没列，但必须做）。

**失败文案映射的顺序是有意的**：网络判在签名之前，但网络正则只收真正的网络关键词（`network|request|\burl\b|dns|timeout|connect|offline|fetch|http`），**不能用裸 `https?`**——签名错误的原文里常带下载 URL，按 URL 判会把签名问题误归为网络，用户会一直重试网络而永远修不好。`\b` 边界防 `design`/`signal` 误命中 `sign`。

**「稍后提醒」存版本号字符串，不存布尔**。存布尔等于永久静音，下次真有新版本用户再也看不到提示；存版本号则只忽略这一个版本，更高版本照弹。

EMA 参数：窗口 1s、α=0.4（新样本权重），约 3 个窗口收敛；首个 chunk 只打点不出速度（没有时间跨度）。

## task-056 M3 技术评估 + 遗留小修（开发轮完成）

分支 `feature/task-056-research-and-cleanup`，8 个提交，已 push。

**4 个单元**：差量更新评估（结论不做）、`restored_at` 迁移 v2、跨盘 rename 补测、G6 定稿豁免。

**最有价值的判断：差量更新「不做」，理由要站得住。**
- Tauri 2 官方 updater **不支持**差量 —— 核查方式是 `grep -ril "bsdiff\|delta\|xdelta" node_modules/.pnpm/node_modules/@tauri-apps/plugin-updater/` **零命中** + 读 `.d.ts`（只有 `download`/`install`/`downloadAndInstall`，`DownloadOptions` 只有 `headers`/`timeout`）。协议层只认「一个完整包 + 一个整包签名」，插差量 = 自建更新通道、丢掉官方验签。
- **关键算术**：4 MB 包在 20 Mbps 下 1.7 秒。差量乐观省 1.2 秒。而 task-055 的进度条+速度显示已经解决了「等待焦虑」这个真痛点 → 绝对收益 <2 秒。
- **成本**：客户端要常驻旧包缓存（用户升级后安装包通常已被删）+ LRU + SHA 校验 + 双验签 + 回退；服务端要改发版流水线 + 相邻版本产物矩阵。6–9 人日且长期维护。
- **替代建议**：`release profile` 瘦身（`lto="fat"` + `codegen-units=1` + `strip=true` + `opt-level="z"`），预计 -20%~35%、1–2 人日。**这个才是该做的。**
- 诚实标注：Rust 二进制差量实际缩减率**本轮未实测**（要两个相邻 release 产物对照，约 1 人日），但即使按最乐观 70% 算结论不变。

**DB 迁移的两个坑**：
1. **测试会连带红**。加 v2 迁移后 `db_schema.rs` 的 `user_version_bumped_to_1` 断言 1 必红；restore 改 UPDATE 后 `safe_box_restore.rs` 的 `n_box == 0` 必红。任务书白名单没列这两个文件 —— **凡改 schema 或改语义，先全局 grep 断言了旧行为的地方**。
2. **「行还在」不等于「可重复恢复」**。旧实现靠 DELETE 让行消失；新实现行还在，靠 `WHERE id=?1 AND status='in_box'` 挡住第二次。这条不变量必须有用例（`restore_twice_second_returns_not_found`）。
3. 造「v1 老库」测试时注意路径是 `<data_root>/data/cdiskcleaner.db`，不是 `<data_root>/xxx.db` —— 我第一次写错，旧行丢了才 debug 出来。

**跨盘测试的写法**：用「运行时检测双盘 + 打印 `[skip]` 后 return」，**不要用 `#[ignore]`**。`#[ignore]` 要人记得加 `--ignored`，本地有双盘也会被静默跳过 = 等于没测。运行时检测则本地自动真跑（本机 C:→D: 真验证了 copy+remove fallback，内容逐字节一致）、CI 单盘自动 skip。
顺带发现：`restore_from_safe_box` 的 `fs::rename` **没有** copy+remove fallback（只有 `delete_file` 有），跨盘恢复直接报 IO 错。已固化为用例，修不修待评估（修法简单但会引入「copy 成功 remove 失败」的新失败模式）。

**G6 的否决理由（重要，以后别再被 warmup 类方案忽悠）**：warmup 自己就是「首次 IPC」，同样会打 `ERR_CONNECTION_REFUSED` —— 只是把命令名从 `rules_check_update` 换成 `app_info`，**红错数量不变**，对「Console 零红」毫无帮助；放 App 挂载还会让每次启动都红一次，暴露面扩大。加上开发轮不做 GUI 测试、无法验证，提交自己验证不了的「修复」比明确豁免更危险。最终写了 5 条判定规则进第三轮清单 §六。
