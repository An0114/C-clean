**结论：发版门禁仍不通过**，但两条问题性质完全不同，必须分开写：

### G7【P1，新】进度条结束时不满 = task-052 的 G1 修复未闭环（真缺陷）
根因三重叠加，已逐段定位：
1. `runner.rs:63-72` `interpolate_percent` 用 `n/(n+50)`，**渐近函数，槽内永远达不到 `to`** → 设计上必须靠编排层补发的「槽位上界 + 收尾 100」两条边界事件才满格。
2. `ipc/progress.rs:118-137` `ThrottledEmitter` 是**纯丢弃式节流**（`<100ms` 直接 `return`，**无 trailing 补偿**）。而 `orchestrator.rs` 那两条边界 emit 恰好紧跟最后一条 item 事件（同毫秒级）→ 极大概率被吞。
3. `Dashboard.tsx:105-110` 在 `await api("scan_start")` resolve 后**立即 `unlisten()`**，即使 100% 已 emit 也可能没派发到回调。

**为什么测试没抓住（关键教训）**：`scan_progress_percent` 集成测试注入的是 **`VecEmitter`，不经过 `ThrottledEmitter`**，收尾 100 必然被记录 → 断言绿。**测试替身绕过了生产链路上的节流器。** 以后凡经过「节流/队列/去抖」的通道，必须有一条走真实包装层的用例。

### G3 现象仍在，但归因历史数据，不能判失败

### 顺带查出：task-052 测试报告的 G3 证据用错字段
测试报告 L3 拿「Items 页 Session 列显示 `#9010/#9009/#9008`」证明 G3 通过，但 **Items 的 Session 列是 `cleanup_item.session_id`（扫描会话号），`safe_box.source_task_id` 是 `cleanup_task.id`（清理批次号）**，完全不同源，不能互证。所以 G3 的 UI 端到端**从未真正验证过**（后端有 `execute_writes_source_task_id` 5 条真实写入用例兜底，代码可信）。评审基于该报告判通过，没察觉。
