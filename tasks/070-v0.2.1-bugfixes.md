### 2. Bug-1 根因：**提权命令名从来没进 argv**（不是 DISM 的问题）

任务书猜的三个方向（提权通道 / DISM 参数 / 本机环境）**都不对**。

真正的根因在 `engine/src/elevation/mod.rs` 的 `run_elevated`：

```rust
let mut all_args: Vec<(&str, &str)> = args.to_vec();
all_args.push(("--result", result_str.as_str()));
let args_string = build_args_string(&all_args);   // ← cmd 参数根本没被用上！
```

`build_args_string` 只把 `(key, value)` 拼成 `--result "path"`，**`cmd` 从头到尾没进过命令行**。提权 exe 收到 `argv[1] = "--result"`，白名单校验不认 → 直接 `EXIT_UNKNOWN_CMD(3)` 退出，**连结果 JSON 都不写**。主进程于是只看到「退出码 3 + 空输出」，前端显示「DISM 分析失败（退出码 3）：」——冒号后面什么都没有，因为确实什么都没拿到。

**三条独立证据**：

1. **直接跑提权 exe 对比两种 argv 形状**：

   ```text
   cclean-elevation.exe --result x.json                → exit 3      ← 用户看到的
   cclean-elevation.exe dism_analyze --result x.json   → exit 4 + {"message":"DISM 退出码 740",...}
   ```

2. **`C:/Windows/Logs/DISM/dism.log` 里没有我们这次调用的任何痕迹**（唯一会话是 `cleanmgr.exe /autocleanstoragesense`），说明 DISM 压根没被启动过。
3. 用户报的「退出码 3」正好等于 `EXIT_UNKNOWN_CMD` 的常量值。

**为什么三个任务都没发现**：`create_restore_point` 走的是同一条路，**也是坏的**。但还原点只在清理含 L2 项时才建，而 Bug-2（所有项都是 L1）让这条路径从来没被走到——两个 bug 互相掩盖。WinSxS 是第一个真正需要提权通道的功能。

**修法**：新增 `build_argv(cmd, args)`，把「命令名 + 参数」的拼装收在一个函数里，两个调用点（`run_elevated` / `run_elevated_streaming`）都改用它。提权 exe 侧加一句诊断：首个 token 以 `-` 开头时明确提示「调用方可能漏传了命令」。

### 3. Bug-2 根因：**脚本把风险等级写死成 `1`**（不是规则不命中）

5 个 `.ps1` 的 `Write-Item` 调用第 4 个实参全是字面量 `1`：

```text
try { Write-Item $category $_.FullName $_.Length 1 } catch { ... }
```

所以清理列表清一色 L1，L2 永远不可能出现。

顺带确认一件容易误判的事：**`rules/cache_rules.json` 的 `modules` 段在扫描链路上没有任何消费者**。`engine/src/rules/loader.rs` 只把它用于 `whitelist_deny`（外部红线）与格式校验；`grade/` 分级模块在 ARCHITECTURE 里画了但从未实现。**风险等级的唯一来源就是这些脚本**。

因此「往规则库补 L2 规则」对用户可见行为**零影响**，而改 `cache_rules.json` 还要连带改 `rules_meta.json` 里的 SHA-256（loader 会严格比对，改错会让规则库整体加载失败、`external_deny` 也拿不到 → 清理直接报内部错误）。**patch 版不引入这个风险**，故未改规则库。

风险等级判据（已写进各脚本注释）：

| 分类 | 等级 | 理由 |
|---|---|---|
| `edge_cache` / `chrome_cache` | L1 | 浏览器缓存，自动重建 |
| `npm_cache` / `pip_cache` / `pnpm_store` | L1 | 包管理器缓存，下次安装重新下载 |
| `prefetch` | L1 | 预读取缓存，Windows 自动重建 |
| `user_temp` | L1 | 用户自己的临时文件 |
| `windows_temp` | **L2** | 多数文件属 SYSTEM，普通权限删不掉；安装程序/系统服务正在使用，删错会中断安装 |
| `update_download` | **L2** | Windows 更新下载缓存，属 SYSTEM；更新安装中删除会中断更新 |

**实测**（`scan_temp.ps1` 真跑一遍）：`risk=1: 61 条` + `risk=2: 29 条`，两级都出来了；`done` 行仍是 `total_items=90`，NDJSON 协议未变。

### 4. Bug-3 根因：两个独立问题，都出在「整目录移入保险箱」这条新路径上

**① 永久删除失败**

`purge_item` / `purge_expired` / 配额 evict 三处都用 `fs::remove_file`。保险箱以前只放单个文件，所以从没暴露；task-067 起残留扫描用 `delete_dir` 把**整个目录** rename 进来，对目录调 `remove_file` 必然失败（拒绝访问/是目录），一路冒到前端只剩「永久删除失败：内部错误」。

**② 来源列显示「历史（无来源）」**

`SafeBoxDeleter::new(box_dir, conn, None)` 传了 `None`，`safe_box.source_task_id` 恒为 NULL，而 UI 的来源列读的就是它。

**用户真实数据取证**（只读打开 `%APPDATA%\com.and0114.cclean\data\cdiskcleaner.db`，未做任何修改）：

```text
safe_box 共 5 行：
  id=1  src=None  status=restored  68299903B  C:/Program Files\HONOR          ← 目录
  id=2  src=1     status=in_box     1982892B  C:/Windows/Prefetch/...Trace3.fx ← 文件
  id=3  src=1     status=in_box     2007687B  C:/Windows/Prefetch/...Trace5.fx ← 文件
  id=4  src=None  status=in_box       17599B  C:/Program Files\Zero G Registry ← 目录
  id=5  src=None  status=in_box    68299903B  C:/Program Files\HONOR          ← 目录
```

与用户描述完全吻合：**扫描清理来的两个文件条目来源是 `#1`（正确），残留移入的三个目录条目来源全是 NULL**。磁盘上核对：`src=None` 的三条全是**目录**，`src=1` 的两条是文件——正好解释了为什么「永久删除」只在残留条目上失败。

**修法**：

- 抽 `remove_entry()`：`symlink_metadata` 判类型，目录 `remove_dir_all`、文件 `remove_file`、`NotFound` 当成功。用 `symlink_metadata` 而非 `metadata` 是刻意的——不跟随符号链接，避免把指向箱外的链接当目录递归删。
- 移入前先建一条 `cleanup_task` 行当批次，id 传给 deleter，结束后回填真实成功/失败计数。三个刻意的取值：
  - `freed_bytes = 0`：同盘移入保险箱只是 rename，**一个字节都没释放**，不能抬高「累计释放空间」；
  - `dry_run_snapshot` 写 `{"source":"residual_scan",...}`：表里没有 kind 列，这是不破 schema 的唯一标记位；
  - `session_id = NULL`：残留扫描不属于任何一次扫描会话。
- 建行失败时只丢来源、不让整个移入失败——文件该移还是要移走。
