# 立项决策记录（Project Decisions Log）

> 本文档固化立项阶段（2026-10-11）用户逐项拍板的关键决策。
> 后续如发生变更，必须以新决策条目追加（保留历史，不删改旧条目）。

## 决策 #1 · 技术栈最终方案

- **决策**：Tauri 2（Rust 核心 + Web 前端）为最终技术栈，**无 Plan B**。
- **演进路径**：分两期演进引擎——
  - M1：Tauri 壳通过白名单 IPC 调用现有 5 个 PowerShell 脚本（脚本改输出 JSON 流），跑通核心闭环；
  - M2+：扫描 / 分级 / 执行逐步以 Rust 重写，DISM / 注册表等系统 API 保留为提权子进程。
- **影响**：删除原设想中".NET 8 WPF 作为 Plan B"的备选路径；M0 技术验证必须以 Tauri 2 为唯一目标。

## 决策 #2 · Cargo.lock 入库策略

- **决策**：本项目为应用（非库），`Cargo.lock` **必须入库**，以保证发布可复现。
- **落地**：`.gitignore` 中已移除对 `Cargo.lock` 的忽略。
- **影响**：CI / 发布构建必须使用仓库内 `Cargo.lock` 锁定的依赖版本。

## 决策 #3 · 保险箱默认参数

- **决策**：
  - 默认容量上限：**5 GB**；
  - 写满时：**自动淘汰最旧文件**（按 `quarantined_at` 升序，先进先出）；
  - **V1 保险箱只放在 C 盘**，路径为 `%LOCALAPPDATA%\CDiskCleaner\SafeBox`；
  - 跨盘移动（如清理其他盘文件时）的策略推迟到 V2 再评估，V1 不实现。
- **影响**：
  - 保险箱表 `safe_box` 需增加 `quarantined_at`（淘汰排序键）字段；
  - 保险箱容量监控需在清理执行前做预检（预计移入量 + 已用量 > 5GB 时先触发淘汰）；
  - 不实现"保险箱迁移到其他盘"的设置项（V1 UI 不出现该选项）。

## 决策 #4 · 规则库托管与校验

- **决策**：
  - 托管位置：**GitHub Raw**（直接托管在本仓库 `rules/` 目录下，通过 raw.githubusercontent.com 拉取）；
  - 版本与校验：沿用已设计的 `rules_meta.checksum`（SHA-256）；
  - **不加代码签名**。
- **影响**：
  - 规则库热更新逻辑 = 拉取 `rules/cache_rules.json` + `rules_meta.json` → 本地比对 checksum → 一致则替换；
  - 不引入签名验证依赖，简化 M1 实现；
  - 安全边界：仅拉 JSON，永不执行远端代码（该约束不变）。

## 决策 #5 · 代码签名预算

- **决策**：**不购买 EV 代码签名证书**。
- **影响**：
  - 接受 Windows SmartScreen 首次运行警告（在 README 与发布说明中告知用户）；
  - **仍必须走杀软白名单流程**：Microsoft Defender for Endpoint 提交、火绒 / 卡巴斯基等厂商白名单渠道——清理工具被杀软误报是最大发行风险，不能省；
  - 发布说明中需要提供"为何需要放行"的技术解释。

## 决策 #6 · 平台范围

- **决策**：**完全不做 macOS / Linux**，不留"只读分析版"的长期可能。
- **影响**：
  - 架构设计中所有系统 API 调用（DISM、注册表、WMI、UAC）都按 Windows 专属设计；
  - 不引入任何跨平台抽象层，避免为"可能支持其他平台"过度设计；
  - README 与发布渠道文案明确"仅 Windows"。

## 决策 #7 · 多 Agent 切分粒度

- **决策**：**按业务模块 A~F 切分，不按技术层（UI / 引擎 / 规则库）切分**。
- **切分矩阵**：
  | Agent | 负责模块 | 核心范围 |
  |-------|----------|----------|
  | Agent-A | 应用缓存清理 | 通用缓存扫描、50+ 关键词、包管理缓存 |
  | Agent-B | 系统临时与日志 | 17 类系统固定路径、WER、Minidump、更新缓存 |
  | Agent-C | 系统组件存储 | WinSxS DISM 分析与安全清理向导 |
  | Agent-D | 已卸载残留 | 注册表 ↔ 目录交叉比对、空文件夹 |
  | Agent-E | 系统级大文件 | 休眠文件、Windows.old、回收站、大文件地图 |
  | Agent-F | 注册表健康 | Run 键、残留键、计划任务、`.reg` 备份 |
- **影响**：
  - 每个业务 Agent 端到端负责该模块的扫描规则、风险分级、清理逻辑、UI 区块；
  - 公共能力（保险箱、DryRun、审计日志、IPC 框架、SQLite schema）由 M0 / M1 主 Agent 先建好，再给 6 个业务 Agent 复用；
  - 任务拆分与并行开发以 A~F 为边界。

## 决策 #8 · PROJECT_STATE.md 写入时机

- **决策**：`PROJECT_STATE.md` **由 M0 负责人在 M0 启动当天首次写入**，立项阶段不预先创建。
- **影响**：
  - 当前基线中 `docs/` 与 `tasks/` 仅以 `.gitkeep` 占位，不创建 PROJECT_STATE.md；
  - M0 负责人需在启动当天基于本文档 + 设想文档首次落盘 PROJECT_STATE.md，并在其中标注当前阶段、下一步、已完成项。
