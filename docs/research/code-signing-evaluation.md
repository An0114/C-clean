# 代码签名技术评估（M4 遗留 B 中）

> 评估人：DevFullstackRustReact　日期：2026-10-29　任务：task-058 单元 3
> 结论摘要：**当前不做**。不是"买不起"，而是"买了也解决不了主要问题，还要改造发版链路"。给出三个「该做」的触发条件。详见 §6。

## 1. 现状与问题

| 项 | 现状 |
|---|---|
| 分发方式 | GitHub Releases 上传 NSIS `.exe` + MSI `.msi`（用户手动下载安装） |
| 签名 | **未做代码签名**（无 EV / OV 证书） |
| 用户首次运行 | Windows SmartScreen 弹「Windows 已保护你的电脑」→ 需点「更多信息 → 仍要运行」 |
| 已有的签名 | 只对 **updater 差量包**做了 minisign 签名（`TAURI_SIGNING_PRIVATE_KEY`），那是**更新通道的完整性校验**，与 Windows 的**发布者身份认证**是两件事，不能互相替代 |
| 发版方式 | GitHub Actions 全自动（`release.yml`），无人工介入 |
| 用户量 | 内部/小范围，无公开下载量统计 |

**要区分两个概念**（很多讨论把它们混为一谈）：

1. **SmartScreen 声誉**：决定"用户首次运行时是否被拦"。由证书类型 + 下载量/时间共同决定。
2. **发布者身份**：签名后 Windows 属性页会显示"数字签名者：XXX"，用户能确认"这软件没被篡改、确实出自某人"。

买证书**同时**买到这两样，但只有第一样影响"用户能不能顺利装上"。

## 2. 关键约束（2023-06 起的行业规则，比价格更重要）

CA/Browser Forum 的 **Code Signing Baseline Requirements** 自 2023-06-01 起强制：

> **所有代码签名私钥必须存放在硬件加密模块中**（USB token / HSM / 云 HSM），不得以文件形式（`.pfx`）存在。

**这条对我们的直接影响是致命的**：

| 环节 | 现状 | 有证书后 |
|---|---|---|
| 构建 | GitHub Actions 自动跑 | 不变 |
| **签名** | 不需要 | **必须接触硬件私钥** → GitHub Actions 的 ubuntu/windows runner **读不到你插在家里的 USB token** |
| 所以要么 | — | ① 发版改成"CI 构建 → 下载产物 → 本地插 token 手动签名 → 手动上传 Release"（**破坏全自动发版**）；② 或买**云签名服务**（私钥在云 HSM，CI 通过 API 调） |

也就是说：**买证书只是第一步，真正的成本在"如何让 CI 能签名"**。这一条在评估 EV/OV 价格时经常被忽略。

## 3. 四个方案对比

| 维度 | **A. EV 证书** | **B. OV 证书** | **C. 自签名** | **D. Microsoft Store / winget** |
|---|---|---|---|---|
| 年成本 | ~$300–600 | ~$150–300（如 Certum ≈ €209） | 免费 | 上架免费（Store 需 $19 一次性开发者账号） |
| 私钥形态 | **必须硬件**（token / 云 HSM） | **必须硬件**（同左，2023 新规） | 文件即可 | 由 Store 代签（你不需要证书） |
| SmartScreen 首次运行 | **立即信任**（EV 直接建立声誉） | 仍会拦，需**积累 reputation 1–3 个月**（靠下载量） | **必然拦**，且声誉永远建立不起来 | **不拦**（走 Store 安装通道） |
| 发布者身份显示 | 有（公司名） | 有（公司名） | 有但显示"未知发布者"，且证书不受信任 | 有（Store 页面） |
| CI 自动化 | 需云 HSM 或手动签名 | 同左 | 可用文件私钥，CI 友好 | 需接入 Store 提交流程 |
| 申请门槛 | **需企业实体**（营业执照 / D-U-N-S 等） | 需企业实体（部分 CA 对个人开放但审查严） | 无 | 需通过上架审核（隐私政策 / 功能完整性） |
| 适用场景 | 面向公众分发、下载量大 | 同左但预算紧 | **仅内部/自用** | 想借 Store 流量 |

### 3.1 补充：Azure Artifact Signing（原 Trusted Signing）

这是 2024 年后最受关注的低成本方案：微软官方云签名服务，**私钥在 Azure 云 HSM**，CI 通过 API 调用，天然解决 §2 的"CI 拿不到硬件"问题。基础套餐约 **€8.54/月（≈€102/年）**，远低于 EV/OV。

**但有两个硬门槛，对本项目是决定性的**：

1. **地域限制**：个人开发者的公开预览仅面向**美国 / 加拿大**；其它地区（含中国）**需要组织实体**才能开通。欧盟区亦仅限组织。
2. **实体要求**：需要可验证的组织身份（部分场景要求成立满 3 年）。

> **采购前必须自行向 Microsoft 确认中国区个人开发者的可行性**——本文档的结论按"个人开发者、中国大陆、无企业实体"这一前提给出。若实际可用，它会是性价比最高的选项（成本降到 ~€102/年且 CI 友好），届时应重新评估。

## 4. 本项目为什么现在不做

四条理由，按权重排序：

1. **用户量太小，SmartScreen 的伤害有限**。当前是内部/小范围分发，用户第一次点"更多信息 → 仍要运行"的成本，远低于买证书 + 改造发版链路的成本。声誉机制的本质是"用下载量换信任"，没有量就买不到声誉（OV 尤其如此：花了钱仍要等 1–3 个月）。
2. **EV/OV 都要企业实体**。本项目是个人项目，申请 EV/OV 需要营业执照/D-U-N-S 等，不是"花钱就能买"。
3. **改造发版链路的代价被低估**。§2 已说明：硬件私钥与 GitHub Actions 天然冲突。要么把全自动发版降级为"手动插 token 签名"（每次发版多 10 分钟人工 + 出错风险），要么再买云签名服务（又多一个依赖和账单）。
4. **签名解决不了真正的信任问题**。用户不装一个陌生清理工具，主要顾虑是"会不会误删我的文件"，不是"发布者是谁"。这个顾虑靠 **开源代码 + 保险箱 + dry-run 预览 + L3 红线**解决，签名帮不上。

## 5. 如果将来要做，最小路径

| 步骤 | 内容 | 预估 |

若 Azure 不可用 → 走 OV（~€209/年）+ 云 HSM（额外 ~€100–200/年）或手动签名流程，成本翻倍。

## 6. 结论

### 6.1 决策

**当前不做代码签名。** 在 `PROJECT_STATE`「已知问题」里保留为**明确接受的已知项**，并在 README / Release 说明里**主动告知用户**："首次运行会被 SmartScreen 拦截，请点『更多信息 → 仍要运行』"——把预期管理好，比花钱买证书更有效。

### 6.2 三个「该做」的触发条件（满足任一即重新评估）

1. **公开分发且下载量达到数百/月** —— 此时 OV 的 reputation 才可能积累起来，投入才有回报；
2. **出现企业/机构用户** —— 他们的 IT 策略常直接禁止运行未签名程序，签名从"体验优化"变成"准入条件"；
3. **要上 winget / Microsoft Store** —— winget 对未签名包的审核更严，Store 则要求签名或走 Store 代签。

### 6.3 现在就做的低成本替代（已落地，无需额外成本）

| 措施 | 状态 |
|---|---|
| README / Release 说明写明 SmartScreen 绕过步骤 | 待补（建议下次发版时加到 Release notes） |
| 提供 SHA-256 校验值，让用户能自证下载完整 | 待补（`latest.json` 已有签名，但用户不一定知道） |
| 开源代码，用户可自行构建 | 已满足 |
| 数据安全靠保险箱 + dry-run + L3 红线，而非签名 | 已落地（task-003/016/040） |

> 价格与政策均为 **2026-10 公开信息**，采购前需复核：CA/B Forum 规则可能再变、Azure 的地域政策可能放宽、各 CA 报价差异大。
