# 差量更新技术评估（M3 立项前置）

> 评估人：DevBackendRustReact　日期：2026-10-28　任务：task-056 单元 1
> 结论摘要：**不建议做差量更新**。理由不是"做不出来"，而是"省下的绝对量太小、引入的复杂度太大"。建议改为「包体瘦身」这一更有性价比的方向。详见 §6。

## 1. 现状与问题

| 项 | 现状 |
|---|---|
| 更新包 | NSIS `C-DiskCleaner_0.1.6_x64-setup.exe` **4.01 MiB**；MSI **5.83 MiB** |
| 前端资源 | `dist/` 打包产物 **184.22 kB**（gzip 59.18 kB），单 JS chunk |
| 更新方式 | 全量下载（`@tauri-apps/plugin-updater` 的 `downloadAndInstall`） |
| 进度反馈 | task-055 已落地（百分比 + 已下载/总量 + EMA 速度） |
| 签名 | minisign（`bundle.createUpdaterArtifacts` + `TAURI_SIGNING_PRIVATE_KEY`），`.sig` 与安装包成对 |
| 发版频率 | v0.1.0 (10-13) → v0.1.5 (10-23) → v0.1.6 (10-28)，约 **5–10 天一个版本**，且都是 patch 级 |

**表面问题**：每次更新都下 4 MB，慢网下用户要等。

**但先把绝对量摆出来**：

| 网络 | 4 MB 全量下载耗时 |
|---|---|
| 100 Mbps（家用宽带） | ≈ 0.34 s |
| 20 Mbps（一般 4G） | ≈ 1.7 s |
| 5 Mbps（弱网/限速） | ≈ 6.7 s |
| 1 Mbps（极差） | ≈ 34 s |

只有后两档能感受到"久"，而这两档用户占比很低。这是后面「值不值得做」的核心前提。

## 2. 候选方案 A：Tauri 2 官方 updater 的差量支持

**结论：不支持。**

**核查方式（不是猜，是查本地依赖）**：

```bash
$ grep -ril "bsdiff\|delta\|xdelta" node_modules/.pnpm/node_modules/@tauri-apps/plugin-updater/
（无输出）
```

`@tauri-apps/plugin-updater@2.13.3` 的 `dist-js/index.d.ts` 里 `Update` 类只有三个动作：

```ts
download(onEvent?: (p: DownloadEvent) => void, options?: DownloadOptions): Promise<void>;
install(): Promise<void>;
downloadAndInstall(onEvent?: (p: DownloadEvent) => void, options?: DownloadOptions & InstallOptions): Promise<void>;
```

`DownloadOptions` 只有 `headers` / `timeout`，`InstallOptions` 只有 `restartAfterInstall`，**没有任何差量/补丁相关字段**。

**架构层面的原因**：Tauri updater 的协议是「`latest.json` → `{ version, pub_date, platforms: { "windows-x86_64": { url, signature } } }`」，`url` 指向**一个完整安装包**，`signature` 是对该包整体的 minisign 签名。整条链路（下载 → 验签 → 执行安装器）都假设「拿到的东西就是完整包」。要插差量，必须绕过这条链，等于**自建更新通道**，失去官方 updater 的验签与回退保障。

**评估**：直接排除。不是「官方暂时没做」，而是「协议本身不为此设计」。

## 3. 候选方案 B：bsdiff4

**原理**：服务端对相邻版本的两个**完整二进制**做 diff 生成 `.bsdiff` 补丁；客户端拿旧文件 + 补丁本地 patch 出新文件。经典用于二进制（Chromium、Firefox 曾用）。

| 维度 | 评估 |
|---|---|
| Rust 生态 | `bsdiff` crate 存在但维护活跃度一般；官方实现依赖 bzip2 压缩，需要 `bzip2` crate（C 依赖，交叉编译要额外配置） |
| 压缩率 | 对**同源**二进制很好（>90% 缩减）；对**重新编译**的二进制差 |
| 速度 | patch 需要内存里同时持旧包 + 新包（约 8–10 MB），可接受 |
| 适用性 | **这里是最大问题**，见下 |

**致命问题：我们的"旧文件"是安装包，不是应用二进制。**

用户升级后，NSIS 安装包 `.exe` 通常**已经被删掉**（用户不会留着）。要 patch，必须：
1. 让应用在安装后把安装包复制到 `%APPDATA%\com.and0114.cclean\cache\`（多占 4 MB 磁盘），或
2. 从**已安装的应用二进制**（`C-DiskCleaner.exe`，约 8–10 MB 未压缩）patch 出新安装包——但 NSIS 安装包 ≠ 应用二进制的简单封装（它含压缩、卸载器、脚本段），无法从应用 exe 反推安装包。

方案 1 是唯一可行路径，代价：每个用户常驻 4 MB 缓存 + 缓存生命周期管理（清理策略、版本错配处理）。

**另一个问题：Rust 重新编译的二进制差量效果不稳定。** 相邻版本即使只改几行代码，链接器布局、内联决策、符号顺序都可能大范围移动，bsdiff 在这种输入上实测缩减常在 20–50%（不是理论上的 90%）。也就是说 4 MB 的包，差量包可能仍有 2–3 MB。

## 4. 候选方案 C：xdelta3

| 维度 | bsdiff4 | xdelta3 |
|---|---|---|
| 算法 | 后缀排序，压缩率高 | 滚动哈希（Rabin 指纹），速度快 |
| 内存 | 高（需整文件索引） | 低（可流式） |
| Rust 绑定 | `bsdiff` crate（一般） | `xdelta3` crate 多为 FFI 包装（要 C 工具链）；纯 Rust 实现少且不成熟 |
| 压缩率 | 略高 | 略低 |
| 速度 | 慢（秒级，4 MB 尚可） | 快（毫秒级） |
| 成熟度 | 中 | 中偏低（Rust 侧） |

**在 4 MB 这个量级，两者的速度差异感知不到**（都是亚秒级），所以选型只会看压缩率和生态成熟度——而这两项 bsdiff 略优。**xdelta3 没有带来决定性优势。**

## 5. 关键决策点（若真要做）

| 决策点 | 问题 | 若做的方案 |
|---|---|---|
| **差量包签名** | 现有 `.sig` 是对整包的 minisign 签名，差量包是另一个文件，不能复用 | 差量包单独签一份 `.bsdiff.sig`；patch 完成后再校验新包的整包签名（**双验签**，否则中间人可投毒补丁） |
| **旧版本校验** | patch 必须保证「本地旧包 = 服务端生成补丁时用的那个旧包」 | 服务端在 `latest.json` 里为每个补丁标注 `from_version` + `from_sha256`；客户端 patch 前算旧包 SHA-256 比对，不匹配直接放弃走全量 |
| **产物矩阵** | 每对相邻版本一个补丁 = O(N) 增长；若支持跨版本（v0.1.5→v0.1.7）则是 O(N²) | 只支持**相邻版本**（v0.1.6→v0.1.7），跨版本一律全量。即使这样，每发一版就要为上一版生成补丁，且要保留历史安装包 |
| **回退路径** | patch 失败、验签失败、旧包缺失、磁盘不足 | 全部回退到全量下载；回退必须对用户透明（不能让用户看到"更新失败"） |
| **本地旧包留存** | 用户升级后安装包被删/被清理软件清掉 | 应用启动时把安装包复制到 app_data，并做 LRU（只留最近 1 个版本） |
| **CI/发版改造** | 现在 `release.yml` 只产全量包 + 一份 `latest.json` | 要加：拉上一版 Release 资产 → 生成补丁 → 签补丁 → `latest.json` 增加 `patches` 段 → 上传 |

## 6. 结论

### 6.1 推荐方案

**不做差量更新，维持全量下载。**

### 6.2 为什么不值得做（四条硬理由）

1. **绝对收益太小**：包 4 MB，全量在 20 Mbps 下 1.7 秒。差量即便按乐观 70% 缩减算，也只省 1.2 秒——用户感知不到，而 task-055 已经给了进度条和速度显示，"等待焦虑"这个真实痛点已经被解决。
2. **成本远超收益**：客户端要常驻旧包缓存（+4 MB 磁盘）+ LRU + SHA 校验 + 双验签 + 回退；服务端要改发版流水线、维护产物矩阵、保留历史包。**保守估计 6–9 人日**，且是长期维护负担（每次发版都要确认补丁链路没坏）。
3. **脱离官方更新通道**：Tauri updater 的协议不支持差量，自建等于自己维护一条「下载 → 验签 → 安装」的并行链路。安全面（补丁投毒、降级攻击）要自己扛，而这条链路的正确性直接关系用户机器安全。
4. **差量效果本身不确定**：Rust 重新编译的二进制布局漂移会让实际缩减率远低于理论值，可能只有 20–50%。花了 8 人日，实际只省 1–2 MB。

### 6.3 更值得做的替代方向（建议另立小任务）

如果目标真的是「减小更新负担」，按性价比排序：

| 方向 | 预期收益 | 工作量 | 说明 |
|---|---|---|---|
| **① 包体瘦身** | **可能 -20%~35%** | 1–2 人日 | `[profile.release]` 加 `lto = "fat"`、`codegen-units = 1`、`strip = true`、`opt-level = "z"`；前端已单 chunk 184 kB，可再按 tab 做动态 import |
| ② 只在「有大版本」时提示 | 减少打扰 | 0.5 人日 | 当前是"有任何新版本就弹"，改为 patch 级静默、minor 级才弹 |
| ③ 更新包走 CDN / 分地域 | 弱网用户提速 | 0.5 人日 | Releases 资产已走 GitHub CDN，国内可考虑镜像 |
| ④ 差量更新 | 乐观 -50%~70%（实际不确定） | **6–9 人日** | 本文档结论：不做 |

**① 是最划算的**：不改架构、不碰安全链路、纯构建配置，一次改动对所有用户生效，且顺带减小安装包和磁盘占用。建议先做 ①，做完再看是否还需要差量。

### 6.4 立项建议

- **不立项 task-057（差量更新）**。
- 建议改为立项 **task-057（可选）：release profile 瘦身 + 前端按 tab 代码分割**，验收口径为「NSIS 包从 4.01 MiB 降到 ≤3.2 MiB，启动时间不劣化」。
- 若未来包体增长到 >20 MB（例如引入大模型本地推理、内置大资源），**重新评估**差量更新的性价比——那时收益才够。
